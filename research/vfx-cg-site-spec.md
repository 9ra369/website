# VFX/CG情報サイト 基本仕様書

> 対象: 日本語で運営し、扱う情報の大半が海外発。更新頻度は低め（週1〜月数本を想定）。
> 目的: 「一度決めれば以後ずっと使い回せる部分」だけを確定させる。個別記事の内容は含まない。

---

## 0. 設計の前提

### 0-1. このサイトの構造的な強みと弱み

**強み（ここで戦う）**
日本語話者が海外のCG/VFX情報にアクセスするとき、最大の障壁は「そのツール名・技術名を知らないこと」ではなく、**知っていても中身が判断できないこと**にある。原語の固有名詞をそのまま残しつつ、日本語で「何ができるのか」「なぜ重要なのか」を1行で言い切る──これが提供価値の本体。翻訳ではなく**要約と文脈付与**。

**弱み（ここでは戦わない）**
速報性。3D人は2010年からほぼ毎日、MODELING HAPPYは2014年から通算2,400記事以上（242ページ分）を積み上げている。この物量には勝てない。したがって**フロー型（新着ニュース）を主戦場にしない設計**にする。

### 0-2. 3つの設計原則

1. **ストック優先** — トップの主役は「最新記事」ではなく「まとめ（ハブ）記事」。
2. **軸は直交させる** — 分類軸を入れ子にしない（理由は 1-1）。
3. **テンプレートで書く** — 毎回レイアウトを考えない。書く時間の9割を「調べる・理解する」に回す。

## 1. 情報設計（IA）

### 1-1. 先行事例の分析から得た結論

MODELING HAPPY のカテゴリ構成を実データで見ると、**工程軸がソフト軸の下にネストされている**。

```
blender (1,988)
  ├ モデリング 275
  ├ UV展開 47
  ├ テクスチャ&マテリアル 273
  ├ アドオン 1,098   ← blender記事の55%
  ├ リグ 30
  └ ...
MAYA (634)
  ├ モデリング 243   ← 名前が重複
  ├ UV展開 41        ← 名前が重複
  ├ テクスチャ&レンダリング 69
  ├ リグ 24
  └ ...
モデリング 261        ← トップレベルにも別個に存在
未分類 84
```

ここから読み取れる問題が3つある。

| 問題 | 具体 | 対策 |
|---|---|---|
| 軸のネスト | 「UV展開の記事を全部見る」ができない。blender配下とMAYA配下に分断されている | 工程とソフトを**独立した2軸のフラットタグ**にする |
| 巨大カテゴリ | `アドオン` が blender記事の55%。半分が入るカテゴリは絞り込みとして機能しない | 1タグの記事数が全体の25%を超えたら分割する運用ルールを持つ |
| 分類漏れ | `未分類 84` | 必須タグをフロントマターで機械的に強制する |

一方、**ヘッダーナビが「カテゴリツリー」ではなく「まとめページ4本」**（Blenderアドオン / MAYAの使い方まとめ / 無料素材 / おすすめ3DCGパソコン）になっている点は、そのまま採用する。カテゴリツリーはサイドバー/フッターに置き、ナビは編集意図でキュレーションした入口にする。更新頻度が低いサイトほどこれが効く。

CGPress が **Tutorials を「By subject」と「By software」の2枚看板**にしているのも同じ発想で、こちらが正解。

### 1-2. 採用するタグ体系

**3軸すべてフラット。階層なし。1記事に各軸から1〜3個。**

**軸A: topic（領域）** — 記事の主題。以下から選ぶ（増やすときは慎重に）

```
fx / modeling / lookdev / lighting-rendering / animation-rigging
compositing / pipeline / realtime / gis-digitaltwin / ai
hardware / industry / career
```

**軸B: tool（ソフトウェア・技術）** — 記事に出てくる固有名詞。**原語表記・小文字ハイフン区切り**

```
houdini / blender / maya / nuke / unreal / usd / python / substance
zbrush / davinci / comfyui / ...（記事を書くたびに追加してよい唯一の軸）
```

**軸C: type（記事タイプ）** — 1記事に必ず1つだけ

```
brief      紹介・速報（短い）
explainer  解説・深掘り
hub        まとめページ（常時更新）
note       雑記・所感
```

**運用ルール**
- topic は必須・最低1つ。tool は0個でも可（業界動向記事など）。type は必ず1つ。
- 一覧カードに表示するタグは **primary（topic の先頭1つ）だけ**。カードにタグを並べない。
- 記事本文の下部では全タグを表示してよい。

### 1-3. URL設計

```
/                       トップ
/posts/{slug}           記事（type問わず全部ここ。パスにカテゴリを含めない）
/topics/{topic}         領域別一覧
/tools/{tool}           ソフト別一覧
/guides/{slug}          ハブ記事（= type:hub の別名パス、恒久リンク扱い）
/archive                全記事の年別リスト
/about                  サイトについて・更新方針
/feed.xml               RSS
```

**重要**: 記事URLにカテゴリを含めない（`/blender/posts/xxx` にしない）。分類は後から必ず変わる。パスに分類を焼き込むとリダイレクト地獄になる。

slug は **英数小文字ハイフン、原語の固有名詞をそのまま使う**。日本語スラッグ・日付スラッグは使わない。

```
◯ /posts/rbdlab-1-4-blender-destruction
◯ /posts/usd-hydra-storm-overview
✕ /posts/2026/08/28/
✕ /posts/blenderのアドオン紹介
```

## 2. 記事テンプレート

記事は3型しかない。書き始める前にどれか決める。

### 2-1. Type A: brief（紹介・400〜800字）

海外ツール/技術の紹介。**この型が全記事の6割を占める想定**。所要20〜40分。

```markdown
（リード1文）
{開発者・組織}による{何のためのツールか}「{原語名}」が{公開された/更新された}。

## これは何か
2〜4文。何を解決するツールなのか。前提知識のない読者向け。

## 何が新しいか / なぜ気になるか
- 箇条書き2〜4個。事実ベース。
- 「すごい」ではなく「何がどう変わるか」を書く。

## 触れておきたい点
制約・価格・注意点。1〜3行。なければ省略可。

<SourceBox>   ← 後述の固定コンポーネント

## 関連
- 自サイト内の関連記事 1〜3本
```

**リード1文のテンプレ**（3D人の型を踏襲）は「誰が・何を・どういう状態か」を必ず含める。読者はここだけ読んで離脱してもよい。

### 2-2. Type B: explainer（解説・2,000〜5,000字）

自分で調べた/試したことを書く。**このサイトの差別化はここに全部乗る**。所要は数時間〜。

```markdown
## TL;DR
- 3行。結論から。

## 背景 / なぜこれが出てきたか
海外の文脈をここで補う。日本語読者が一番落としがちな部分。

## {疑問形の見出し}
本題。見出しは「〜とは」ではなく「なぜ〜なのか」「〜はどう動くか」の形にする。

## 実際に試す
コード・スクリーンショット・検証結果。1つでも自分の手を動かした痕跡を入れる。

## 制約・注意点

## まとめ

<SourceBox>
## 参照した資料
- 一次ソースへのリンク一覧（英語のまま + 1行の日本語要約）
```

### 2-3. Type C: hub（まとめ・常時更新）

`/guides/{slug}` に置く。**更新頻度が低いサイトの生命線**。新規に書かず、既存記事を束ねて作る。

```markdown
## このページについて
何をまとめているか、誰向けか。2〜3文。

## 目次（自動生成）

## {セクション}
### {項目}
- 1〜3行の説明
- → 詳しくは自サイト記事へ / 一次ソースへ

## 最終更新
YYYY年MM月DD日
```

**hubは5本もあれば十分**。例:
- Houdini のパイプライン/TD系ツールまとめ
- USD を理解するための資料まとめ（英語ソース中心・日本語解説つき）
- GIS × 3DCG のデータソース一覧
- 海外CG/VFX情報サイト一覧（自分の情報源の公開）
- 用語対訳表（4-3参照）

## 3. フロントマター定義

静的サイトジェネレータ（Astro / Next.js / Hugo など）前提。**この形を最初に確定させ、以後変えない。**

```yaml
---
title: "RBDLab 1.4 — クリック操作だけで破壊エフェクトを組めるBlenderアドオンが更新"
slug: "rbdlab-1-4"
date: 2026-08-28          # 公開日（不変）
updated: 2026-08-28       # 内容を見直したら更新
type: brief               # brief | explainer | hub | note
topics: [fx]              # 必須・1〜3
tools: [blender]          # 0〜3
summary: "破壊シミュレーションのセットアップをUIから行えるBlenderアドオンの最新版。フラクチャからハンドリングまでを1画面に集約している。"
                          # 60〜100字。カード・OGP・meta descriptionで共用
hero: "/images/posts/rbdlab-1-4/hero.webp"
hero_credit: "© RBDLab Studio"      # 他者素材なら必須
source:
  name: "RBDLab Studio"
  url: "https://..."
  lang: en
draft: false
---
```

**設計意図**
- `summary` を1つ持たせて、カード表示・OGP description・meta description・RSS の4箇所で使い回す。書くのは1回。
- `updated` を持つことで、古い記事に「最終更新」を出せる。低頻度運用では**公開日より最終更新日のほうが誠実で有用**。
- `source` を構造化して持つことで、SourceBox を自動描画できる（手打ちしない）。

## 4. タイトル規約

一度決めれば以後ずっと効く、最も費用対効果の高い部分。

### 4-1. 基本形

```
{原語の固有名詞}{ バージョン} — {何ができるか（動詞で終える）}{カテゴリ名詞}
```

先行2サイトはどちらもこの形を採っている。

```
3D人:            RBDLab 1.4 - ポチポチクリックするだけで、エフェクト付き破壊表現を
                 手軽に追加出来るBlenderアドオン!
MODELING HAPPY:  Lazy Select – 「1・2・3」が不要!マウスオーバーで面・エッジ・頂点を
                 直感的に選択できる無料Blenderアドオン
```

**なぜこの形か**: 日本語話者がこの情報に辿り着く経路は、ほぼ例外なく「英語のツール名で検索する」か「SNSで英語名を見かける」。原語がタイトル先頭にないと発見されない。一方、原語だけでは中身が分からないので、後半の日本語が判断材料になる。**この2つを1行で両立させるのが、日本語×海外情報サイトの中核仕様。**

### 4-2. ルール

| 項目 | 規約 |
|---|---|
| 全体長 | 全角60字以内 |
| 先頭32字 | 検索結果で切れる位置。**固有名詞と核心の動詞をここに収める** |
| 固有名詞 | 必ず原語表記。カタカナに直さない（「ブレンダー」ではなく `Blender`） |
| 読み仮名 | 必要なら本文の初出時に1回だけ括弧書き。タイトルには入れない |
| セパレータ | 半角スペース + `—`（emダッシュ）+ 半角スペースに統一。`-` `｜` `【】` を混在させない |
| `【】` | 状態限定バッジのみ許可: `【無料】`『【期間限定】』`【日本語対応】`。内容の説明には使わない |
| `!` | 使わない。1記事に1つまで、本当に例外的な場合のみ |
| バージョン | 半角、スペース区切り（`RBDLab 1.4`）。`v` は公式表記に従う |
| 数字 | 半角 |
| 禁止語 | 「すごい」「必見」「話題の」「〜すぎる」「知らないと損」 |

### 4-3. 型別の例

```
brief      Rodin Gen-2 — テキストと画像から製品レベルの3Dメッシュを生成するモデルが公開
brief      【無料】Simple Photogrammetry — オープンソースのフォトグラメトリツールが登場
explainer  USDのCompositionを理解する — LIVRPSの評価順を実例で追う
explainer  なぜHoudiniのHDAはパイプラインの単位になるのか
hub        GIS × 3DCG で使えるデータソースまとめ
note       2026年上半期に読んだVFXパイプライン関連の資料
```

### 4-4. 用語対訳の固定

海外情報を継続して訳すなら、**訳語を固定した対訳表を最初に作る**。数年書き続けると必ず表記ゆれが出る。

```
procedural   → プロシージャル（「手続き型」にしない）
node graph   → ノードグラフ
shading      → シェーディング
look dev     → ルックデブ
asset        → アセット
scatter      → 散布 / スキャッター（文脈で使い分け、初出時に併記）
```

自サイトの `/guides/glossary` として公開すれば、それ自体がハブ記事になる。

## 5. 画像・レイアウト規約

### 5-1. 規格（全部固定）

| 用途 | サイズ | 形式 | 上限 |
|---|---|---|---|
| ヒーロー画像 | 1600 × 900（16:9） | WebP | 200 KB |
| OGP | 1200 × 630 | PNG/WebP | 300 KB |
| 本文内画像 | 幅1600px以内、高さ自由 | WebP | 250 KB |
| 自作図解 | 1200 × 675 | SVG優先、なければWebP | — |

**カード用サムネは別途用意しない。** ヒーロー画像を `object-fit: cover` の16:9枠で表示する。比率を複数持つと、クロップ位置のズレ事故と作業量が両方増える。

### 5-2. レイアウトルール

- 本文カラム幅は **最大680〜720px**（日本語の可読行長は全角35〜40字）。
- **本文内画像は常にカラム幅いっぱい**。左右回り込み（float）は使わない。CGWORLD.jpの日本国内アクセスは約7割がモバイルで、回り込みは破綻する。
- 画像の直後に必ず**キャプション1行**。画像だけを置かない。
- 画像を横に並べない。比較したいときは**上下に並べてキャプションで対比を書く**か、before/afterスライダー1種類だけをコンポーネント化する。
- GIFは使わない（重い）。動きが必要なら動画埋め込みかWebPアニメ。
- 動画は**埋め込み優先**（YouTube / Vimeo / X）。自分でホストしない。

### 5-3. 他者素材の扱い（海外情報を扱う以上、ここは仕様として明文化する）

- 使ってよいのは、**公式が配布しているプレスキット・スクリーンショット・公式動画のサムネ**まで。
- それ以外は「自分で撮ったスクリーンショット」か「埋め込み」に置き換える。
- 使う場合は `hero_credit` に `© {権利者}` を必ず入れ、画像下に表示する。空欄なら**ビルドを落とす**（仕組みで強制する）。
- 出典が用意できない記事は、ヒーロー画像なしで公開してよい。その場合はタイポグラフィだけのプレースホルダーを自動生成する（5-4）。

### 5-4. OGP自動生成

`title` と `topics` からOGP画像をビルド時に自動生成する仕組みを最初に作る。Satori / `@vercel/og` / Playwright など。

- 背景: サイトのブランドカラー1色
- テキスト: タイトル（自動改行・3行まで）
- 左下: サイト名 / 右下: primary topic

これがあると「画像がないから公開できない」という詰まりが消える。**低頻度運用では、公開を止める要因を潰すことが最優先。**

## 6. UI / UX 仕様

### 6-1. トップページ（低頻度前提の構成）

上から順に:

1. **サイトの説明1行** — 「海外のCG/VFX/パイプライン関連の情報を、日本語でまとめています。」
   → 更新が3ヶ月止まっていても、このサイトが何なのかは伝わる。
2. **Start here — ハブ記事カード 3〜5枚**（手動固定）
   → ここが主役。ナビゲーションの実質的な本体。
3. **最新記事 6〜9枚**
4. **トピック別入口**（タグクラウドではなく、カード or 名前付きリスト。件数を添える）
5. **購読導線** — RSS / X / メール

> 「最新記事」を最上部に置かない。低頻度サイトのトップに古い日付が最初に出ると、それだけで死んで見える。

### 6-2. 記事カードの情報要素（固定）

```
┌──────────────────┐
│  [16:9 サムネイル]     │
├──────────────────┤
│  fx                  ← primary topic 1つだけ
│  タイトル（2行でクランプ） │
│  summary（2行でクランプ） │
│  2026.08.28          ← 日付は最後・小さく
└──────────────────┘
```

- 著者名は出さない（個人サイトなのでノイズ）。
- タグを複数並べない。
- MODELING HAPPY の一覧が「カテゴリ1つ + タイトル + 日付」だけで成立している通り、これで足りる。

### 6-3. 記事ページ

上から: パンくず / タイトル / summary / 公開日・最終更新 / primary topic / ヒーロー画像 / 本文 / **SourceBox** / 全タグ / 関連記事3本 / 購読導線。

**SourceBox（このサイトの署名コンポーネント）**

海外情報を日本語で扱うサイトにとって、最も価値のある固定パーツ。フロントマターの `source` から自動描画する。

```
┌─ 一次ソース ─────────────────┐
│ 開発元    RBDLab Studio           │
│ 公式      https://...     [開く]  │
│ 価格      $49（買い切り）          │
│ 対応      Blender 4.2 以降        │
│ ライセンス  商用利用可              │
│ 発表      2026-08-20              │
└──────────────────────────┘
```

Art of VFX が全記事末尾に置いている「WANT TO KNOW MORE?」ブロック（公式ページ・関連する自前記事・視聴先への3リンク）と同じ役割。**1記事をハブ化して回遊を生む**。日本語読者にとっては「で、どこで手に入るの/いくらなの」という最頻出の疑問への回答でもある。

項目は記事ごとに増減してよいが、**「公式リンク」だけは必須**とする。

### 6-4. 一覧ページ（/topics/, /tools/）

- 上部にそのタグの説明文を1〜3行（手書き、一度書けば固定）。SEOにも効くし、初見の読者への案内にもなる。
- 記事カードのグリッド。ページングは番号式（無限スクロールにしない。低頻度なら件数も多くない）。
- ページ末尾に「関連するトピック」を3つほど。

### 6-5. その他の画面仕様

- **検索**: Pagefind などのビルド時静的検索。**原語と日本語の両方でヒットする**ことが必須要件（タイトルに原語が入っている前提が効く）。
- **RSS**: 必須。この分野の読者はFeedlyを常用する。`summary` を description に入れる。
- **ダークモード**: あってよいが優先度は低い。1系統で作り込む方が良い。
- **コメント欄**: 作らない。低頻度サイトでは管理コストが価値を上回る。反応はSNSで受ける。
- **/about に更新方針を明記**: 「不定期更新です」と書く。これが期待値を調整し、更新が空いても信頼を損なわない。CGPressが「ボランティア運営」と明示しているのと同じ効果。

## 8. 段階的な立ち上げ

**Phase 1（まず動くものを）**
トップ / 記事 / `/topics/` / RSS / `/about`。テンプレは brief のみ。X からの移植分を `type: brief` として流し込む。ハブ記事は1本だけ作る。

**Phase 2（差別化）**
SourceBox と OGP自動生成を導入。explainer を書き始める。`/tools/` を開放。

**Phase 3（資産化）**
ハブ記事を5本まで増やす。用語対訳表を公開。検索を追加。
