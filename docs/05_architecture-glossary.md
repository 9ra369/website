# システム設計解説（専門用語つき）

このプロジェクト（Merge VFX&CG）が現時点でどう組み上がっているかを、使われている設計パターンの名前とあわせて説明します。各用語は本文中で**太字**にし、末尾の[用語集](#用語集)で改めて解説します。

## 1. 全体構成

リポジトリは役割ごとに4つの層に分かれています。**関心の分離（Separation of Concerns）**の考え方で、それぞれが独立して差し替え可能になるようにしてあります。

```
_raw/       … Xアーカイブの生データ（gitignore対象、個人情報を含む）
_work/      … パイプラインの中間生成物（gitignore対象、再生成可能）
content/    … 正規化済みのコンテンツ本体（Markdown + Frontmatter）
scripts/    … content/ を作る・整形するETLパイプライン（Node.js）
prototype/  … 現在の見た目（静的HTML/CSS。将来Astroに置き換え予定）
data/       … categories.json など、サイト全体で共有する構造化データ
docs/       … 仕様書・設計ドキュメント
```

`_raw`/`_work`だけ**非破壊（Non-destructive）**の原則が特に強く効いていて、削除ではなく常に「移動」で不要データを扱います。これはやり直しのコストをゼロに近づけるための設計判断です。

## 2. コンテンツパイプライン（ETLパターン）

Xポストをサイト記事に変換する仕組みは、データ基盤の世界で**ETL（Extract, Transform, Load）**と呼ばれる古典的なパターンをそのまま採用しています。

| フェーズ | 内容 | 該当スクリプト |
|---|---|---|
| **Extract**（抽出） | Xの公式アーカイブ（`tweets.js`）から生データを取り出す | `01-normalize.js` |
| **Transform**（変換） | 振り分け・重複排除・**スレッド結合**・タイトル/要約のAI生成 | `02-triage.js`, `10-merge-hashtags.js` |
| **Load**（書き出し） | 正規化した結果をMarkdown（**Frontmatter**付き）→HTMLとして永続化 | `05-write-markdown.js`, `08-build-tip-pages.js` |

ポイントは、各フェーズが**冪等（べきとう、Idempotent）**であること。同じ入力に対して何度実行しても同じ結果になるように作ってあるので、閾値やルールを変えて「何度でもやり直せる」という要件（仕様書§4）を満たしています。

### スレッド結合アルゴリズム

自己リプライで連なる投稿を1記事にまとめる処理は、木構造（ツリー）の走査に近い考え方です。各投稿を「親投稿への参照を持つノード」とみなし、

1. 親子関係のマップを作る
2. 親が持つ子が1件だけ（＝**分岐（Branching）**していない）の場合だけ連結する
3. 分岐している場合は連結せず、各子を独立したノードとして残す

という規則で処理しています。最初の実装では分岐時に子ノードを取りこぼすバグがあり、これは典型的な「**エッジケース（Edge Case）**の考慮漏れ」でした。

### 信頼度ベースのトリアージ（Human-in-the-loop）

AIが生成したタイトルの確信度（`confidence: high/low`）によって、自動的に`content/posts/`（そのまま採用）と`content/_triage/`（要確認）に振り分けています。これは**Human-in-the-loop**と呼ばれる設計で、「AIが自動化できる部分は自動化しつつ、判断に迷う部分だけ人間の確認を挟む」という考え方です。仕様書が最初から「全自動にはしない」と明言していたのはこの設計思想の表れです。

## 3. データモデル

### Single Source of Truth（信頼できる唯一の情報源）

カテゴリの定義は`data/categories.json`という1つのファイルにだけ存在し、サイトのCSS（`thumb-tips`などのクラス名）もドキュメントもこのファイルの`slug`を参照する形にしています。これを**Single Source of Truth（SSOT）**と呼びます。同じ情報を複数箇所にハードコードすると、片方だけ更新して食い違う「**データの不整合（Inconsistency）**」が起きやすくなるため、それを避ける設計です。

### Frontmatter / YAML

各Markdownファイル冒頭の`---`で囲まれた部分を**Frontmatter**と呼びます。中身は**YAML**（人間にも読みやすいデータ記述形式）で、`title`や`tags`といったメタデータをMarkdown本文と分離して持たせるための業界標準的な手法です（Astro・Hugo・Jekyllなど主要なSSGが共通して採用）。

### スラッグ（Slug）

`environment`や`tips`のような、URLやファイル名にそのまま使えるID文字列を**スラッグ（Slug）**と呼びます。日本語の表示名（例:「Environment」）とは別に持たせることで、表示名を変更してもURL構造が壊れないようにしています。

## 4. プレゼンテーション層（見た目）

### 静的サイト生成（SSG）

現在の`prototype/`はNode.jsスクリプトでMarkdownからHTMLを直接書き出す、簡易的な**静的サイトジェネレーター（Static Site Generator, SSG）**の自作実装です。将来的にAstroへ移行する計画（`docs/01_tech-stack.md`）があり、その際は`content/`のFrontmatterスキーマがそのまま**Content Collections**（Astroが提供する型安全なコンテンツ管理機能）に載り替わる設計にしてあります。

### デザイントークン（Design Tokens）

`style.css`の`:root`に定義した`--color-bg`や`--radius-md`のような変数は**CSS Custom Properties**（俗に**デザイントークン**）です。色や余白の値を1箇所で管理し、テーマ変更時の修正範囲を最小限にするための仕組みです。

### レスポンシブな画像サイズ調整

サムネイル画像の縦横比を「元画像に合わせる」修正では、`aspect-ratio`（要素の縦横比を指定するCSSプロパティ）と`object-fit`（画像を枠にどう収めるか、`cover`＝切り抜き／`contain`＝収める、を指定するプロパティ）、それに`:has()`（子要素の有無で親要素のスタイルを分岐させる**CSSセレクタ**）を組み合わせています。

## 5. 品質管理

- **重複排除（Deduplication）**: 画像再投稿などによる同一文面の投稿を検出し、情報量の多い方だけを残す
- **非破壊編集（Non-destructive Workflow）**: 不要判定したデータも削除せず`_archive/`へ移動するのみ
- **バージョン管理（Version Control）**: Gitでの変更履歴管理。`.gitignore`で個人データ（`_raw/`）や再生成可能な中間データ（`_work/`）をリポジトリ管理の対象外にしている

## 用語集

| 用語 | 解説 |
|---|---|
| ETL（Extract, Transform, Load） | データを「抽出→変換→書き出し」の3段階に分けて処理する、データパイプラインの基本パターン |
| 冪等性（べきとうせい, Idempotency） | 同じ処理を何度実行しても結果が変わらない性質。安全に再実行できることを保証する |
| Human-in-the-loop | AIによる自動処理の中に、人間の確認・判断を意図的に挟む設計思想 |
| エッジケース（Edge Case） | 通常想定するパターンから外れる、境界的・例外的な入力条件 |
| Single Source of Truth（SSOT） | ある情報について「ここを見れば正しい」と言える唯一の管理場所を1つに絞る設計原則 |
| Frontmatter | Markdownファイル冒頭に`---`で囲んで書く、YAML形式のメタデータ領域 |
| YAML | インデントで階層を表す、人間にも読みやすいデータ記述形式（JSONの親戚） |
| スラッグ（Slug） | URLやファイル名に使う、半角英数字中心の短い識別子文字列 |
| SSG（Static Site Generator） | Markdown等のコンテンツから、あらかじめ完成したHTMLファイル群を生成する仕組み・ツール（Astro, Hugo, Next.jsなど） |
| Content Collections | Astroが提供する、Frontmatterのスキーマを型定義してバリデーションできる機能 |
| デザイントークン（Design Tokens） | 色・余白・角丸などのデザイン値を変数として一元管理する仕組み（CSSでは`--color-bg`のようなCustom Propertiesで実装） |
| CSS Custom Properties | `--変数名: 値;`の形で定義し`var(--変数名)`で参照する、CSSのネイティブな変数機能 |
| `aspect-ratio` | 要素の縦横比（幅:高さ）を指定するCSSプロパティ |
| `object-fit` | `<img>`などの内容物を、指定した枠にどう収めるか（`cover`=はみ出た部分を切り抜き、`contain`=枠内に収める）を指定するCSSプロパティ |
| `:has()` | 「特定の子要素を持つ要素」を選択できるCSSセレクタ。条件分岐的なスタイリングが書ける |
| 重複排除（Deduplication） | 同一・類似データが複数ある場合に、不要な重複を取り除く処理 |
| 非破壊編集（Non-destructive Workflow） | 元データを削除せず、複製・移動・フラグ付けなどで扱うことで、いつでも元に戻せる状態を保つ編集方針 |
| Version Control（バージョン管理） | ファイルの変更履歴を記録し、任意の時点に戻したり差分を確認できるようにする仕組み（Gitなど） |
| `.gitignore` | Gitの管理対象から特定のファイル・フォルダを除外するための設定ファイル |
| 関心の分離（Separation of Concerns） | システムを役割ごとに分割し、それぞれが独立して変更・差し替えできるようにする設計原則 |
